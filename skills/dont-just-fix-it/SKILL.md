# dont-just-fix-it

사용자가 개선 사례 기록을 요청하거나 이 스킬을 호출했을 때 실행한다. 작업 중 개선을 발견했다는 이유만으로 문서를 만들지 않는다.

개선 작업을 다른 사람이 근거까지 확인할 수 있는 사례로 남긴다. 문장을 쓰기 전에 작업 맥락, 접근 가능한 코드와 증거를 확인한다. 사용자의 명시적 범위·시간·도구 제약을 우선한다. 문서화에 충분한 기존 근거가 있으면 재측정하지 않는다. 채택하지 않은 실험도 이유가 있으면 기록한다.

## 1. 비교 기준 정하기

- 변경 코드와 호출 경로, 기존 사례 문서를 읽고 사용자 증상과 원인 가설을 구분한다. 문서화 요청만으로 관련 없는 최적화를 추가하지 않는다.
- 변경 전·후 상태를 커밋, diff 또는 별도 사본으로 식별한다. 이미 끝난 작업은 저장된 측정 자료부터 찾는다. 기준 상태를 복원할 수 없으면 전후 개선율을 만들지 않는다.
- 해당 개선을 설명하는 지표를 고른다. API는 응답 시간·쿼리 수, 배치는 실행 시간·메모리, CI는 빌드 시간처럼 분야에 맞게 비교한다. 초기 로딩은 FCP·LCP·전송량, 애니메이션은 프레임 간 이동 폭·긴 작업처럼 증상을 설명할 수 있는 지표를 쓴다. 레이아웃·카피 변경은 전후 스크린샷으로 비교한다.

## 2. 측정하고 증거 보존하기

새 측정이 필요하고 허용된 경우에만 아래 절차를 적용한다. 기존 결과만 정리하는 요청이면 출처와 조건을 확인하고 3단계로 넘어간다.

- 프로젝트의 기존 빌드·측정 도구를 우선 사용한다. 웹 성능은 개발 서버가 아닌 프로덕션 빌드로 비교한다. 특정 프레임워크나 MCP를 전제로 하지 않는다.
- 작업 트리와 실행 중인 서버를 먼저 확인한다. 가능하면 별도 작업 디렉터리에서 비교한다. 기존 변경을 덮어쓰거나 일괄 stash하지 않고, 포트 번호만 보고 프로세스를 종료하지 않는다. 종료가 필요하면 소유와 용도를 확인한다.
- 입력 데이터·실행 환경을 맞춘다. 웹이면 브라우저·뷰포트·CPU/네트워크 설정·캐시 상태·오리진을 맞춘다. 같은 포트에 순차로 띄우거나, 포트가 다르면 오리진·캐시 차이를 통제하고 기록한다. 공유 빌드 디렉터리를 쓰는 서버와 빌드를 동시에 돌리지 않는다.
- 조건별 최소 3회, 애니메이션처럼 편차가 큰 측정은 가능하면 5회 실행하고 지표별 중앙값과 회차별 값을 남긴다. 반복이 불가능하면 단일 측정임을 밝히고 그 한계 안에서 해석한다. 성능 측정과 다른 무거운 검사는 순차 실행한다.
- 감속 측정이 필요하면 동일한 설정을 양쪽에 적용한다. CPU 감속은 실제 저사양 기기의 재현이라고 단정하지 않는다. Lighthouse 시뮬레이션, 로컬 브라우저 관측값, 실사용자 지표를 구분한다.
- DOM 존재와 실제 노출은 다르다. opacity 기반 노출을 재면 조상 opacity도 반영하고 임계값을 적는다. 이 값만으로 가림·화면 밖 배치까지 포함한 실제 가시성을 입증했다고 쓰지 않는다. 프레임 위치 샘플도 실제 표시된 프레임 수와 구분한다.
- 캐시가 결과를 흔들면 새 브라우저 컨텍스트 등으로 조건을 맞춘다. 타임아웃·실패를 0으로 바꾸거나 불리한 회차를 조용히 제외하지 않는다.
- 재현 스크립트는 개인 설치 경로를 하드코딩하지 않고 프로젝트 상대경로와 명시한 도구 의존성을 사용한다.
- 회차별 값, 단위, 도구 버전, 설정, 명령, 비교 상태를 문서와 함께 보존한다. 전체 보고서를 보관하지 못하면 추출한 JSON임을 명시한다. 새 실행이 기존 근거를 덮어쓰지 않게 한다.
- 도구나 기준 자료가 없으면 측정하지 못한 항목을 밝힌다. 추정치를 실측값으로 채우지 않는다.

## 3. 결과와 회귀 확인하기

- 접근 가능한 코드가 있으면 측정한 상태와 최종 반영 상태를 비교한다. 코드가 없거나 기록만 전달받았으면 그 한계를 밝히고 원인을 코드로 확인했다고 쓰지 않는다. 중간 최고 점수나 회귀가 있던 구현을 최종 성과로 쓰지 않는다.
- 변경과 관련된 동작을 확인한다. 모달이면 열기·닫기·키보드·포커스 복귀, 시각 변경이면 관련 뷰포트·테마·모션 감소 설정처럼 영향 범위에 맞춘다. 실제 실행한 검사만 적는다.
- 스크린샷은 비교 조건을 맞춰 `docs/issue/assets/<사례-slug>/`에 저장한다. 애니메이션 정지 프레임이나 저장 보고서 캡처라면 그 사실을 캡션에 적는다. alt에는 화면에 보이는 내용을 쓴다.
- 단계명이나 수치 변화만으로 특정 단계의 구현·버그·채택 여부를 추정하지 않는다. 작업 기록이 명시한 사실과 측정에서 관측한 차이를 구분한다.
- 채택·보류·되돌림을 구분한다. 누적 실험의 단계별 차이를 독립 효과로 더하지 않는다. 개선이 작은 경우, 악화된 지표, 추가 비용, 미달 목표도 함께 남긴다.

## 4. 사례 작성하기

사용자가 지정한 위치와 기존 문서 형식을 우선한다. 없으면 `docs/issue/NN-<사례-slug>.md`에 다음 구조를 쓴다. 문서 언어는 사용자 또는 저장소 관례를 따른다. 한국어는 `~했습니다`체로 작성한다.

````markdown
# <사용자 증상 또는 개선 결과> (`<프로젝트>`)

- **Skills & Libraries**: <실제로 사용한 기술>
- **작업 일자**: YYYY.MM.DD
- **대상**: <화면·모듈>

- **문제**— <사용자가 겪은 증상과 확인된 기준값>
- **원인**— <코드·측정으로 확인한 구조적 원인. 가설은 구분>
- **해결**— <변경 내용과 채택 또는 보류 이유>
- **결과**— <전후 수치 또는 시각적 차이, 비용·한계>
````

증거가 없는 표·코드·이미지 칸은 채우지 말고 생략한다. 기존 자료를 사용했다면 출처와 당시 조건을 적고 새로 측정한 것처럼 쓰지 않는다. 수치 차이는 반올림 전 값으로 계산한다.

## 마무리

문서 수치를 저장된 자료와 대조하고 로컬 링크·이미지 경로를 확인한다. 임시 설정과 자신이 띄운 프로세스를 정리하고, 중지했던 개발 서버는 원래 상태로 복구한다. 문서화 요청만으로 커밋·푸시·공개를 수행하지 않는다.
